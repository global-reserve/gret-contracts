## 1. Summary

### Scope

In scope, with the code line counts given in the audit brief:

- `contracts/GRETVault.sol` (814): the GRET ERC-20 and the basket vault: mint, redemption,
  rebalancing, basket changes, fees, governance, the optional eligibility contract and liquidation.
- `contracts/ChainlinkPriceGuard.sol` (150): prices each swap with Chainlink feeds and enforces a 2%
  loss limit per swap and per week.
- `contracts/IPriceGuard.sol` (10) and `contracts/IEligibility.sol` (5): the interfaces the vault calls.

Out of scope: `contracts/mocks/`, `scripts/`, the tests, OpenZeppelin Contracts 5.6.1 itself (how the

`scripts/pilot/` was read only for context (the pilot basket, its feeds and its redemption flow). The
specification states that this source has not been deployed (docs/SPECIFICATION.md:3-4), so every code

Deployment and trust model, as given in the brief: Ethereum mainnet; Solidity 0.8.38 with the
optimizer and EVM `cancun`; the vault relies on EIP-1153 transient storage; the per-transaction gas cap

Chainlink feeds for the guard. Adversaries: any user or MEV searcher; a token issuer that freezes,
upgrades, rebases, charges fees, calls back or answers malformed data; a rebalancer bounded only by the
guard; and a governance that turns hostile but must respect the vault's seven-day notices.

- A finding that needs governance or the rebalancer to break an operating assumption names it and is rated

- Wording that the code or the rest of the specification contradicts without changing behavior, NatSpec
  and events are Informational.

### The central question

The brief asks whether holders that may redeem can always leave during a notice. They cannot, in every
case:

- **What holds.** Every delayed action is enforced exactly at its boundaries:
  - Execution is refused before `readyAt` and after the execution window.
  - A holder's redemption one second before `readyAt` succeeds, for all seven delayed actions.
  - The mint pause never applies to redemption, and a fee raise needs its own notice.
  - A component made to fail can be skipped with `redeemSkipping`.
- **What fails.** A hostile governance can make every redemption whose basket version is fixed before
  execution revert in every block of a whole notice (GRET-01).
  - A holder keeps an exit only through a transaction that reads `basketVersion()` and `components()`
    when it executes: a router after an approval, a smart account, or an EIP-7702 delegation.
  - With an eligibility contract that approves holders as callers, the router is refused too. Only code
    running at the holder's own address gets out.
- **After the fix.** From `c107549` on, a redemption with zero minima, or none, is not tied to the basket
  version. A holder who also lists every token announced for the basket leaves in every block of a notice
  (section 8).

### Main recommendations

1. Let a redemption without positional limits run without a basket version, or limit how often the
   basket can change. Provide and document a same-transaction exit (GRET-01).
2. Make the guard notice unit changes of priced components and bound swaps that look fair, or revoke the
   rebalancer around such changes (GRET-05).
3. Read component balances with a bounded copy and a gas stipend, in the vault and in the guard (GRET-03).
   Fix the write order in `checkSwap` (GRET-02).
4. Correct the specification and NatSpec statements listed in each finding.

### Fix review

After this report was written, the owner asked for every finding to be addressed before publication, one
commit per finding (two for GRET-15): five fixed in code and eleven documented. The auditor wrote the
changes at the owner's request, so section 8, which reviews them, is not independent.

- GRET-01 is fixed in `c107549` and `6356b01`:
  - A redemption whose minima are all zero, or that has none, no longer depends on the basket version.
  - `redeemSkipping` accepts announced tokens in its list before they join.
  - At most 128 tokens can be announced and waiting at once.
  - A holder can now prepare an exit that no basket change refuses during a notice.
- GRET-05 is partly fixed in `8ed0664`:

  - A split applied through a multiplier can still be mispriced. It is now a documented known limitation,

- GRET-04, GRET-06, GRET-13 and GRET-15 are documented as known limitations, each with a test that
  reproduces it.
- GRET-07, GRET-08, GRET-10, GRET-11, GRET-12, GRET-14 and GRET-16 are corrected in the specification,

## 3. Findings in detail

### GRET-01: A hostile governance can refuse every fixed-version redemption for a whole notice

**Severity:** High. **Likelihood:** Low.

**Location.**

- contracts/GRETVault.sol:
  - :1198-1201: `_requireBasket`, which `redeem` (:340) and `redeemSkipping` (:359) call first.
  - :605: `announceComponent`, with no limit on the number of announcements.
  - :624-637: `addComponent`, callable by anyone; `++basketVersion` at :635.
  - :644-665: `removeComponent`, governance, immediate; `++basketVersion` at :663.
  - :1087-1093: `_requireEmpty`.
  - :349-351: the NatSpec of `redeemSkipping`.
- docs/SPECIFICATION.md:128-134, :190-192, :408-410; KL-1 (:454-464).

**Description.**

Both normal-mode redemptions revert with `BasketChanged` unless the caller's `version` equals
`basketVersion` and the minima array has the current length. In normal mode no holder can leave without
passing that check. Liquidation claims need no version, but only governance can open liquidation (:405).

How governance keeps changing the version:

- `basketVersion` grows by one on every `addComponent`. Anyone may execute it for a token announced 7 to
  14 days earlier.
- It also grows on every `removeComponent`. Governance executes it at once for any component that holds
  nothing or dust and was not written off.
- Governance can announce any number of contracts whose `balanceOf` answers 0. `_requireEmpty` returns on
  a zero balance before it reads `decimals`, so a five-byte contract is enough.
- With N announcements made 7 to 14 days earlier, governance can change the version 2N times in the
  following week, once at the top of every block.
- Every redemption whose `version` was fixed before it executes then reverts. This lasts for the whole
  seven-day notice of an action proposed at the start of that week, for example a rebalancer with a guard
  that accepts every swap.

Holders who lose the exit: every redemption with a version fixed before execution, through either
function. That includes:

- `redeem` or `redeemSkipping` sent from a wallet.
- The pilot redemption flow (`scripts/pilot/plan.ts`, out of scope), which reads `basketVersion` and
  `previewRedeem` and then sends `redeem`.
- Safe or timelock transactions prepared in advance, and any contract that takes the version as a
  parameter.
- `redeemSkipping` is no escape: it checks the version first.

Holders who keep it: those whose transaction reads `basketVersion()` and `components()` when it executes
and passes them on in the same call, skipping every component the holder does not trust.

- The tests show a router used after a plain `approve`, and an EOA delegating to the same code with
  EIP-7702.
- A one-transaction contract using an EIP-2612 `permit` should also work (reasoning, not tested).

An eligibility contract can close even that exit:

- The specification's model for such a contract is that "only approved parties create and redeem"
  (docs/SPECIFICATION.md:249-250).
- The vault asks `canRedeem(msg.sender, to)` (:985, :1169-1176), so a contract that approves holders as
  callers refuses a router with `NotEligible(router, holder)`.
- Only code running at the holder's own address (a smart account or an EIP-7702 delegation) then leaves.

The preparation is public:

- Apart from removing up to 127 empty components already registered, every change of version needs an
  announcement made 7 to 14 days earlier.
- That announcement shows up as `ComponentAnnounced` at least a week before it can be used.
- The specification does not present mass announcements as a threat to exits, and the hostile action
  itself need not be proposed until the churn starts.

Why this is reported although a known limitation mentions it:

- KL-1 says that "a hostile governance can make redemptions prepared for a fixed version revert with
  `BasketChanged`". It does not say that the refusal can last a whole notice, that both redemption
  functions are affected, or that only same-transaction readers escape.
- docs/SPECIFICATION.md:190-192 says that "the notice gives holders time to redeem, skipping a component if
  necessary".
- :408-410 requires healthy exits to remain possible without the admin's cooperation.
- The NatSpec of `redeemSkipping` says that "whoever may redeem can always leave with every component that
  still works".

The consequence is more severe than the known limitation describes.

**Impact.**

- Who is exposed: holders whose transactions fix the version in advance. The positional-limit rule
  (docs/SPECIFICATION.md:128-131), the NatSpec and the pilot redemption flow all lead holders to that
  form.
- What they lose: the seven-day notice protects them from nothing. They are refused for the whole notice
  of any of these actions:
  - a rebalancer with a guard that accepts every swap;
  - an eligibility contract that refuses them;
  - a fee raise;
  - a write-off.
- They then bear what the change takes: in the test, everything.

**Likelihood.** Low:

- Governance must turn hostile.
- The announcements are public at least a week ahead.
- One change per 12-second block over a whole notice costs about 7.7e9 gas. Measured per operation, cold,
  without subtracting refunds:

  | Operation | Gas |
  |---|---:|
  | Deploying a junk contract | 33,194 |
  | `announceComponent` | 31,767 |
  | `addComponent` | 111,509 |
  | `removeComponent` | 45,294 |

- Against redemptions sent privately, the change must land ahead of the holder in every one of the 50,400
  blocks, which could not be tested.
- Against redemptions in the public mempool, one change per attempt is enough.

**Trust assumptions.** A hostile governance that respects every notice, as the brief allows. No operating
assumption has to break: none limits announcements or removals.

**Severity rationale.** For the holders described above this is "a way around the seven-day notices", so
High.

- We considered Medium ("temporary denial of redemption"). Holders who can run same-transaction code
  keep an exit that governance cannot block, as long as no caller-checking eligibility contract is
  appointed.
- We kept High for three reasons:
  - The specification and the project's own redemption flow lead holders to the form that is refused.
  - Nothing tells holders that a same-transaction exit is needed.
  - A caller-checking eligibility contract closes the router exit as well.
- It is not Critical, because a trusted role must misbehave.

**Proof.**

- `test_C01_churnRefusesFixedVersionRedemptionsForAWholeNotice`:
  - Setup: 25,200 junk tokens are announced on day 0. An early `addComponent` reverts with `NotReady`.
    On day 7 a rebalancer and a `MockPriceGuard` that accepts every swap are proposed.
  - Churn: in each of the 50,400 blocks of the notice, the first transaction adds (anyone) or removes
    (governance) a junk token. Bob's redemption, prepared on the previous block's state and alternating
    `redeem` and `redeemSkipping`, reverts with exactly `BasketChanged(seen, seen + 1)`.
  - Asserted: 50,400 refusals, `basketVersion() == 50400`, and the last refusal before `readyAt`.
  - Outcome: at `readyAt` the rebalancer accepts and the guard is applied. Two swaps take both reserves
    for one base unit each, and Bob's redemption then pays 0 of each component.
- `test_C01_sameTransactionReadersLeaveDuringChurn`:
  - After a change at the top of the block, a `redeemSkipping` prepared before it reverts with
    `BasketChanged(0, 1)`.
  - Bob leaves through a router, used after a plain approval, that reads `components()` and
    `basketVersion()`.
  - In the next block, an EOA whose code is an EIP-7702 designator for the same contract leaves in full.
    The designator is written with `vm.etch`, because the test runner cannot sign delegations.
- `test_N02_callerCheckingEligibilityClosesTheRouterExitDuringChurn`:
  - An eligibility contract listing Alice and Bob is applied after its notice. A junk addition then lands
    at the top of a block.
  - Bob's prepared `redeemSkipping` reverts with `BasketChanged(0, 1)`, and his router exit reverts with
    `NotEligible(router, Bob)`.
  - The same code run at Bob's address (EIP-7702) leaves with all his components.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

import {GRETVault} from "../../contracts/GRETVault.sol";
import {MockPriceGuard} from "../../contracts/mocks/MockPriceGuard.sol";
import {GRETVaultCase} from "../helpers/GRETVaultCase.sol";

/// GRET-01: sustained `basketVersion` churn refuses every redemption whose `version` is fixed before it
/// executes, in every block of a whole seven-day notice. Governance announces junk tokens a week
/// ahead (the fuel cannot be used earlier), then proposes a rebalancer with a guard that accepts
/// every swap and bumps the version at the top of each 12-second block of that notice: anyone adds
/// a ready junk token, governance removes it at once. `redeem` and `redeemSkipping` both check the
/// version first, so a holder whose call was prepared on the previous block is refused every time;
/// when the notice ends the reserves are swapped away and the holder's redemption pays nothing.
/// A call that reads the version when it executes still leaves in a block that began with a bump:
/// a router after a plain approval, or an EOA delegating to the same code with EIP-7702.

/// @dev Reads the basket in the same transaction and skips every component not listed in `keep`.
contract SameTxExit {
    /// As a router: pulls the caller's GRET (an approval, which no basket change can block).
    function exitFor(GRETVault vault, uint256 shares, address[] calldata keep) external returns (uint256[] memory) {
        vault.transferFrom(msg.sender, address(this), shares);
        return _exit(vault, shares, msg.sender, keep);
    }

    /// As EIP-7702 delegated code: the account redeems its own GRET, so the vault sees the EOA.
    function exitSelf(GRETVault vault, address[] calldata keep) external returns (uint256[] memory) {
        require(msg.sender == address(this), "only the account itself");
        return _exit(vault, vault.balanceOf(address(this)), address(this), keep);
    }

    function _exit(GRETVault vault, uint256 shares, address to, address[] calldata keep)
        private
        returns (uint256[] memory)
    {
        IERC20[] memory tokens = vault.components();
        address[] memory skipped = new address[](tokens.length);
        uint256 n;
        for (uint256 i; i < tokens.length; ++i) {
            bool kept;
            for (uint256 j; j < keep.length; ++j) kept = kept || address(tokens[i]) == keep[j];
            if (!kept) skipped[n++] = address(tokens[i]);
        }
        assembly ("memory-safe") {
            mstore(skipped, n)
        }
        return vault.redeemSkipping(shares, to, new uint256[](tokens.length), skipped, vault.basketVersion());
    }
}

contract C01VersionChurnTest is GRETVaultCase {
    uint256 internal constant BLOCK_TIME = 12;

    /// @dev Runtime 0x60206000f3 answers every call with 32 zero bytes: `balanceOf` is 0, so the
    /// vault accepts it as a component and removes it at once.
    function _junk() internal returns (address junk) {
        bytes memory init = hex"6460206000f36000526005601bf3";
        assembly ("memory-safe") {
            junk := create(0, add(init, 0x20), mload(init))
        }
    }

    function _announceJunk(uint256 n) internal returns (address[] memory junk) {
        junk = new address[](n);
        for (uint256 i; i < n; ++i) {
            junk[i] = _junk();
        }
        vm.startPrank(GOVERNANCE);
        for (uint256 i; i < n; ++i) {
            vault.announceComponent(junk[i]);
        }
        vm.stopPrank();
    }

    function _keep() internal view returns (address[] memory keep) {
        keep = new address[](2);
        keep[0] = address(healthy);
        keep[1] = address(faulty);
    }

    function test_C01_churnRefusesFixedVersionRedemptionsForAWholeNotice() public {
        vm.prank(BOB);
        vault.mint(SHARE, BOB, _pair(2e18, 5e18), SHARE, 0);
        uint256 blocks = 7 days / BLOCK_TIME; // 50,400 blocks in one notice
        address[] memory junk = _announceJunk(blocks / 2); // each fuels one addition and one removal
        // The fuel is public a week before it can burn: an announced token cannot join earlier.
        vm.expectRevert(abi.encodeWithSelector(GRETVault.NotReady.selector, block.timestamp + 7 days));
        vault.addComponent(junk[0]);
        vm.warp(block.timestamp + 7 days);

        MockPriceGuard guard = new MockPriceGuard(); // accepts every swap
        vm.startPrank(GOVERNANCE);
        vault.proposeRebalancer(REBALANCER);
        vault.proposePriceGuard(address(guard));
        vm.stopPrank();
        uint256 start = block.timestamp;
        (, uint256 readyAt) = vault.rebalancerProposal();

        uint256 refused;
        for (uint256 b; b < blocks; ++b) {
            uint256 seen = vault.basketVersion(); // what a wallet reads before signing
            uint256 count = vault.componentCount();
            vm.roll(block.number + 1);
            vm.warp(start + b * BLOCK_TIME);
            if (b % 2 == 0) {
                vault.addComponent(junk[b / 2]); // anyone may, at the top of the block
            } else {
                vm.prank(GOVERNANCE);
                vault.removeComponent(junk[b / 2]); // immediate
            }
            bytes memory expected = abi.encodeWithSelector(GRETVault.BasketChanged.selector, seen, seen + 1);
            vm.prank(BOB);
            if (b % 4 < 2) {
                try vault.redeem(SHARE, BOB, new uint256[](count), seen) {
                    revert("a prepared redemption went through");
                } catch (bytes memory reason) {
                    assertEq(reason, expected);
                }
            } else {
                try vault.redeemSkipping(SHARE, BOB, new uint256[](count), new address[](0), seen) {
                    revert("a prepared skipping redemption went through");
                } catch (bytes memory reason) {
                    assertEq(reason, expected);
                }
            }
            ++refused;
        }
        assertEq(refused, blocks);
        assertEq(vault.basketVersion(), blocks);
        assertLt(block.timestamp, readyAt); // the last refusal came before the notice ended

        // The notice ends: the rebalancer swaps both reserves away for one base unit each.
        vm.warp(readyAt);
        vm.prank(REBALANCER);
        vault.acceptRebalancer();
        vault.applyPriceGuard();
        vm.startPrank(REBALANCER);
        vault.swap(address(healthy), healthy.balanceOf(address(vault)), address(faulty), 1, "");
        vault.swap(address(faulty), faulty.balanceOf(address(vault)), address(healthy), 1, "");
        vm.stopPrank();
        uint256 version = vault.basketVersion();
        vm.prank(BOB);
        uint256[] memory paid = vault.redeem(SHARE, BOB, _pair(0, 0), version);
        assertEq(paid[0] + paid[1], 0);
    }

    function test_C01_sameTransactionReadersLeaveDuringChurn() public {
        vm.prank(BOB);
        vault.mint(SHARE, BOB, _pair(2e18, 5e18), SHARE, 0);
        address eoa = makeAddr("7702 holder");
        vm.prank(ALICE);
        vault.transfer(eoa, SHARE);
        address[] memory junk = _announceJunk(1);
        vm.warp(block.timestamp + 7 days);
        SameTxExit exit = new SameTxExit();
        vm.prank(BOB);
        vault.approve(address(exit), SHARE);

**Recommended fix.**

The version protects positional limits only (docs/SPECIFICATION.md:128-131), and `redeemSkipping` names
skipped components by address. A redemption without positional limits therefore needs no version. Since
this source is not deployed, any of these code changes works:

- Accept an empty `minAmountsOut` as "no limits" and skip `_requireBasket` in that case. The minima loop
  must then treat a missing entry as zero.
- Take minima keyed by token address.
- Limit basket changes: one addition or removal per day caps a churn at seven changes per notice.

Without a code change:

- Publish a permissionless exit helper. It works with an approval or a `permit`, reads the version and
  the components in the same transaction, and skips the untrusted components the holder lists.
- Make the pilot redemption flow use it, and note that an eligibility policy must check the receiver
  (`to`), not the caller, for such a helper to pass.
- State in KL-1 that a churn can last a whole notice, that only same-transaction readers are immune, and
  that mass announcements are a hostile signal.

### GRET-05: The guard keeps pricing a component by its old unit after a decimals change or a split, so a fair-looking swap can take a whole reserve

**Severity:** Medium. **Likelihood:** Low.

**Location.**

- contracts/ChainlinkPriceGuard.sol:
  - :113: the token decimals are cached at deployment.
  - :176-177: `_value` scales by the cached token decimals and by the feed decimals read live.
  - :131: a swap that looks fair returns before both limits.
  - :44-45: the NatSpec says each feed "must quote one whole token in US dollars, with nothing to
    convert".
- contracts/GRETVault.sol:537-540.
- docs/SPECIFICATION.md:172-173, :177, :524, :537-538; KL-2 (:465-469), KL-10 (:501-504), OA-2 (:424-428)
  and OA-3 (:429-430).

**Description.**

`_value` computes `amount * answer * 1e18 / 10**(tokenDecimals + feedDecimals)`, with `tokenDecimals`
read once, in the constructor. It assumes that one base unit of a priced component is always the same
fraction of what its feed quotes. Two issuer actions break that assumption:

1. **Decimals change.** An issuer upgrades a priced component to new decimals and rescales the balances.
   The guard then misprices every base unit by a factor of 10 to the power of the change in decimals.
   - With more decimals, dust of that token looks like a large amount and buys another priced
     component's whole reserve.
   - With fewer, the vault's whole balance of it looks like dust and goes for dust.
2. **Split applied through a multiplier.** An xStocks-style token lists each balance as internal shares
   times a multiplier. The issuer documentation the specification cites (:524) says a split raises the
   multiplier proportionally, while the feed (SPY-USD for SPYx) prices one share of the underlying.
   Between the multiplier change and the feed's first price after the split, the guard misprices each
   token unit by the split ratio k.
   - If the multiplier moves first, tokens worth 1/k of what the guard credits buy other priced reserves.
   - If the feed moves first, the vault's tokens are valued at 1/k and can be bought for that.

In both cases the guard sees `boughtValue >= soldValue` and returns at :131 without recording anything.
Neither the 2% per-swap limit nor the 2% weekly limit applies, and each reserve goes in one swap.

The specification lists the cached token decimals among the guard's immutable settings (:177), and
"following token-decimal changes" among unapproved roadmap proposals (:537-538). None of the known
limitations or operating assumptions states the consequence:

- KL-2 covers feed lag within deviation thresholds, a token trading below its underlying, and staleness,
  all bounded effects.
- KL-10 says an issuer upgrade can block mint and redemption, not that it turns off the guard.
- OA-3 asks governance to consider pausing minting before a multiplier change, not to stop swaps.
- OA-2 prescribes revoking the rebalancer after an unexpected loss or a depeg, and here no loss is recorded.

**Impact.**

- While the mispricing lasts, a rebalancer can take, without `LossRecorded`:
  - the reserve of every other priced, active component, one swap per reserve; or
  - the changed component's whole reserve.
- Holders bear the loss.
- The six pilot components without a feed are out of reach.

**Likelihood.** Low:

- Decimals change:
  - All eleven components are upgradeable proxies.
  - We know of no decimals change in any of them; this was not checked on chain.
- Split:
  - In the pilot, SPYx is the only priced component that converts amounts to shares, and, as far as we
    know, SPY has never split.
  - For xStocks of single equities, splits are routine.
  - Whether a mispricing window exists on mainnet depends on when the issuer activates a new multiplier
    relative to the feed's update. This was not verified. A stale feed refuses swaps, so the feed must be
    fresh on the wrong side of the split.
- Prevention: a governance that revokes the rebalancer before an announced change prevents it. An
  unannounced decimals change cannot be prevented that way.

**Trust assumptions.** An issuer that upgrades its token or applies a split, which is either the brief's
adversary or a routine corporate action, and a rebalancer bounded only by the guard. No operating assumption
has to break as written.

**Severity rationale.** The impact is in the brief's High class ("a way around ... the guard's limits").
The trigger, though, is an issuer action the attacker does not control and that has no precedent for the
pilot's priced components, so it is rated one level lower.

/// @dev Model of a token that keeps internal shares and lists each balance as shares times a
/// multiplier, the mechanism the xStocks multipliers page referenced by docs/SPECIFICATION.md:524
/// describes for stock splits ("we adjust the multiplier proportionally"). A 4-for-1 split raises
/// the multiplier fourfold, so every listed balance grows fourfold at once while each token unit
/// becomes worth a quarter. Not a claim about the current SPYx code.
contract N01MultiplierToken {
    uint8 public constant decimals = 18;
    uint256 public multiplier = 1e18;
    mapping(address account => uint256) public sharesOf;
    mapping(address owner => mapping(address spender => uint256)) public allowance;

    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    function balanceOf(address account) public view returns (uint256) {
        return sharesOf[account] * multiplier / 1e18;
    }

    function mint(address to, uint256 amount) external {
        sharesOf[to] += amount * 1e18 / multiplier;
    }

    function setMultiplier(uint256 next) external {
        multiplier = next;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        _move(msg.sender, to, amount);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) allowance[from][msg.sender] = allowed - amount;
        _move(from, to, amount);
        return true;
    }

    function _move(address from, address to, uint256 amount) private {
        uint256 shares = amount * 1e18 / multiplier;
        sharesOf[from] -= shares;
        sharesOf[to] += shares;
        emit Transfer(from, to, amount);

### GRET-02: A guard re-applied as its own successor carries an old week's loss into every later week

**Severity:** Low. **Likelihood:** Low.

**Location.**

- contracts/ChainlinkPriceGuard.sol:
  - :136-139: the new week is stored before the predecessor is asked.
  - :183-191: `_inheritedLoss`.
- contracts/GRETVault.sol:
  - :577-580: `proposePriceGuard` accepts the guard already in place.
  - :589-595: `applyPriceGuard` sets `previousPriceGuard` to the outgoing guard.
- docs/SPECIFICATION.md:178-181, :190-191.

**Description.**

`checkSwap` writes `currentWeek = week` (:137) and then sets `weeklyLoss = _inheritedLoss(week)` (:138).
`_inheritedLoss` reads `vault.previousPriceGuard()` and takes that guard's `weeklyLoss()` when its
`currentWeek()` equals `week` (:186-190).

When governance proposes the guard already in place and it is applied, `previousPriceGuard ==
priceGuard`. On its first loss in each new week the guard then asks itself:

- `currentWeek()` already returns the new week, written one line earlier.
- `weeklyLoss()` still holds the total of the last week with a loss.

The specification says two things the code does not do:

- A replacement starts from what its predecessor recorded "in the same week" (:178-181).
- The guard can only be "replaced by another contract" (:190-191). The code accepts the same contract.

As long as the guard is its own predecessor, the 2% weekly budget becomes a single budget that never
renews.

**Impact.** Rebalancing liveness only.

- Once the carried total reaches 2%, every lossy swap reverts with `WeeklyLossTooHigh` in every later
  week, until a different guard is applied after a new notice.
- Fair and favorable swaps still pass (:131). Mint, redemption and liquidation are unaffected, and the
  deviation only ever adds counted loss.
- A variant needs a component with a transfer callback, against OA-1. Applying a ready replacement from
  inside a swap makes the guard that `swap` cached (contracts/GRETVault.sol:528) inherit from itself for
  that swap. It is also conservative.

**Likelihood.** Low. It needs governance to propose the current guard, which is a plausible slip: for
example re-confirming the guard, or "cancelling" a pending replacement by proposing the current guard
instead of calling `cancelPriceGuardProposal`.

**Trust assumptions.** No operating assumption has to break.

**Proof.**

- `test_C02_reappliedGuardStartsANewWeekFromAnOldTotal`:
  - The total of week w0 is x = 236,904,761,904,762, where 1e18 is 100%.
  - In week w0+1 the same lossy swap records 203,692,062,762,488 when the guard is not re-applied (the
    control, from a snapshot), and 440,596,824,667,250 when it is.
  - The test asserts that the second figure equals x plus the control, with
    `previousPriceGuard() == priceGuard()`.
- `test_C02_onceAWeekIsUsedUpLossySwapsStayRefusedInLaterWeeks`:
  - Week w0 is used up (19,999,999,985,989,228).
  - Control: without the re-application, a 1.99% loss on 1/50 of a reserve passes in week w0+1.
  - With it, the same swap reverts with `WeeklyLossTooHigh` in week w0+1 and again ten weeks later.
  - A fair swap still passes.
  - A different guard, applied after a new notice, starts at zero, and the lossy swap passes.

        fFeed.setAnswer(40e8);

        vm.warp(_priceGuardReadyAt());
        _refresh();

    /// feed value (rounded up, plus one unit); returns the revert selector, or zero if it passed.
    function _swap(uint256 divisor, uint256 kept) internal returns (bytes4) {
        uint256[] memory r = vault.reserves();
        bool sellH = a.valueOf(address(healthy), r[0]) >= a.valueOf(address(faulty), r[1]);
        (address sold, address bought, uint256 amount) = sellH
            ? (address(healthy), address(faulty), r[0] / divisor)
            : (address(faulty), address(healthy), r[1] / divisor);

        ) + 1;

        try vault.swap(sold, amount, bought, received, "") {
            return bytes4(0);
        } catch (bytes memory reason) {
            return bytes4(reason);
        }

            if (err == bytes4(0)) continue;

        assertGt(used, 1.99e16);

### GRET-03: One component's oversized `balanceOf` answer blocks every `rescue`; the guard copies a predecessor's answers the same way

**Severity:** Low. **Likelihood:** Low.

**Location.**

- contracts/GRETVault.sol:
  - :1129-1133: `_readableBalance`, a low-level `staticcall` that forwards 63/64 of the gas and copies
    the whole answer before checking `data.length >= 32`.
  - :858-871: both passes of `rescue` read every registered component, including excluded and
    written-off ones.
  - :647 and :1087-1093: a written-off or funded component cannot be removed.
- contracts/ChainlinkPriceGuard.sol:186-189 (`_inheritedLoss`) and :202-204 (`_vaultValue`).
- docs/SPECIFICATION.md:180-181, :228-232; KL-10; OA-7.

**Description.**

The specification promises that a component whose read "reverts or answers with less than one word counts
as zero before the transfer, so it is not compared and does not block rescues of other tokens"
(:230-232). The NatSpec at contracts/GRETVault.sol:1127-1128 generalizes this to any unreadable
component.

That promise fails for an oversized answer:

- A component whose `balanceOf` returns a payload sized to the gas it receives leaves the vault unable to
  pay the memory expansion needed to copy it.
- `rescue` then runs out of gas at every gas limit, for every token. A smaller limit only shrinks the
  answer.

The documented remedies do not help:

- A write-off leaves the component registered, so `rescue` still reads it.
- A written-off component can never be removed.
- Removal also needs an empty balance and normal mode.

The guard copies a predecessor's answers the same way:

- A predecessor whose `currentWeek` answers an oversized payload does not "count as zero" (:180-181).
- Instead it makes every lossy swap of the new guard revert at every gas limit, until a further
  replacement.
- By reading the code, a priced component answering `balanceOf` this way would likewise make `_vaultValue`
  revert lossy swaps.

A read that burns its gas and then answers can also block the second pass of `rescue`. This was measured
with 2 and 11 components.

**Impact.**

- Governance cannot rescue any of these:
  - foreign tokens;
  - ordinary components at zero supply;
  - during liquidation, a removed component that recovered, which OA-7 says to rescue and distribute
    outside the vault.
- The block lasts as long as the issuer keeps the behavior.
- Holders' exits are not affected:
  - The written-off component is excluded.
  - `redeemSkipping` never calls it.
  - Claims of other components do not read it.
- In the guard the effect fails closed: lossy swaps stop and fair swaps pass.

**Likelihood.** Low. It needs the issuer of one registered component to make `balanceOf` answer oversized
data, the brief's issuer that "answers malformed data". All eleven components answer exactly 32 bytes
today, as observed on a fork.

**Trust assumptions.** No operating assumption has to break. The guard case needs a predecessor that was
appointed after its notice and later answers oversized data, for example after a proxy upgrade.

**Proof.**

- `test_C03_oversizedBalanceAnswerBlocksEveryRescue`:
  - Setup: two components, one GRET, and 1e18 of a foreign token in the vault. The component's read
    breaks and governance writes it off.
  - Control: with a reverting read, `rescue(foreign, governance, 1e18)` succeeds at 16,777,216 gas.
  - With the oversized answer, the rescue fails at 1, 4, 8, 12 and 16 million gas and at 16,777,216,
    each time using the whole limit.
  - The foreign token stays in the vault, and `removeComponent` reverts with `TokenWrittenOff`.
  - Alice still redeems her GRET in full.
- `test_C03_oversizedPredecessorAnswerBlocksLossySwaps`:
  - Setup: a contract appointed as guard is replaced by a `ChainlinkPriceGuard`.
  - Control: while the predecessor's `currentWeek` reverts, a swap losing 1.99% passes, because the
    predecessor counts as zero, as specified.
  - With an oversized answer, the same swap fails at every limit from 1 million to 16,777,216 gas, using
    more than 90% of each limit.
  - A fair swap still passes.

/// for the answer's memory (w words cost 3w + w^2/512), so the caller, left with about 40%, cannot
/// pay the same expansion to copy it. Hypothetical issuer or guard behavior, not a current one.
abstract contract OversizedAnswer {
    function _answer(uint256 word) internal view {
        uint256 target = gasleft() * 6 / 10;
        uint256 size = (Math.sqrt(1536 * 1536 + 2048 * target) - 1536) / 2 * 32;
        assembly ("memory-safe") {
            mstore(0, word)
            return(0, size)
        }
    }

### GRET-04: A hostile governance can take a written-off component's recovered balance at once, without notice

**Severity:** Low. **Likelihood:** Low.

**Location.**

- contracts/GRETVault.sol:
  - :807-809: `setMintPaused`, immediate.
  - :949-952: `_mintAmounts` skips excluded components.
  - :669-673: `activateComponent`, immediate.
  - :727-741: `writeOffComponent` excludes the component and pauses minting.
  - :1012-1027: redemption pays the reactivated component.
- docs/SPECIFICATION.md:69-71, :96-97; OA-5 (:433-434); KL-1 (:454-464); KL-3 (:470-476).

**Description.**

A write-off, executed after its notice, excludes a component F and pauses minting. When F becomes
transferable again, governance can do the following in one transaction, using immediate powers only:

1. Resume minting.
2. Mint M GRET, paying only the active components.
3. Reactivate F.
4. Redeem the M GRET, taking M / (S + M) of F and getting its own contribution back.
5. Pause minting again.

Holders cannot react, because the sequence is atomic. The write-off's notice gave them no defense either:
a frozen F cannot be redeemed, so leaving during that notice forfeits F, while staying exposes it.

The known limitations do not describe this outcome:

- KL-3 says that entrants admitted before reactivation "share" the recovery.
- KL-1 lists governance's immediate powers but presents none of them as moving holders' value. It also
  omits resuming minting, which :69 says is immediate.

Combined, governance itself is the entrant and takes nearly all of the recovery. That is more severe than
the known limitations describe.

**Impact.** Holders lose up to M / (S + M) of a written-off component's recovered balance. In the test
that is 99%, using temporary capital of 99 times the active backing, which is returned in full.
Governance's cost is gas.

**Likelihood.** Low. A written-off component with a material balance must become transferable again, and
governance must break OA-5.

**Trust assumptions.** Governance breaks OA-5: "after one executes, reactivate the recovered balance
before resuming minting".

**Severity rationale.** Low because the finding depends on breaking OA-5. Without that dependency it would
be a limited loss (Medium).

**Proof.**

- `test_C04_governanceTakesTheRecoveryWithoutNotice`:
  - Alice holds the only GRET (2 H and 5 F).
  - F is frozen, written off after its notice (minting paused, F excluded), and then recovers.
  - The governance contract resumes minting, mints 99 GRET for 198 H and no F, reactivates F, redeems and
    pauses minting.
  - Governance ends with its 198 H back plus 4.95e18 F.
  - Alice's redemption pays 2e18 H and 5e16 F, instead of 5e18 F.
- `test_C04_oa5OrderLeavesTheRecoveryToHolders`:
  - The same steps, with reactivation first.
  - Governance pays and gets back exactly 495e18 F, and Alice receives 5e18 F.

### GRET-06: The fixed 10-unit receipt tolerance stops covering xStocks once their multiplier exceeds about ten

**Severity:** Low. **Likelihood:** Low.

**Location.**

- contracts/GRETVault.sol:
  - :47-49: `MAX_RECEIPT_SHORTFALL = 10`, whose NatSpec says it "covers tokens that convert amounts to

  - :962-973: `_pull`, with the check at :970. It is used by mint (:304-310) and by the buy side of swaps

**Description.**

/// balance = shares * multiplier and moves floor(amount / multiplier) shares, so a transfer can
/// arrive up to about one multiplier of base units short. At today's SPYx multiplier (about 1.0075)

contract ShareToken {
    uint256 public multiplier = 1_007_474_126_658_766_000; // SPYx, early November 2026
    mapping(address account => uint256) public sharesOf;
    mapping(address owner => mapping(address spender => uint256)) public allowance;

    function setMultiplier(uint256 multiplier_) external {
        multiplier = multiplier_;
    }

    function balanceOf(address account) external view returns (uint256) {
        return sharesOf[account] * multiplier / 1e18;
    }

    function mint(address to, uint256 amount) external {
        sharesOf[to] += amount * 1e18 / multiplier;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        _move(msg.sender, to, amount);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        if (allowance[from][msg.sender] != type(uint256).max) allowance[from][msg.sender] -= amount;
        _move(from, to, amount);
        return true;
    }

    function _move(address from, address to, uint256 amount) private {
        uint256 shares = amount * 1e18 / multiplier;
        sharesOf[from] -= shares;
        sharesOf[to] += shares;
    }

### GRET-07: Expired proposals still read as pending

**Severity:** Low. **Likelihood:** Certain whenever a proposal is left to expire. The impact is only a
false signal.

**Location.**

### GRET-13: GRET dust sent where it can never be handed over leaves liquidation as the only exit for the last GRET

**Severity:** Low. **Likelihood:** Anyone can cause it for a few base units, with nothing to gain.

**Location.**

- contracts/GRETVault.sol:
  - :990-991: the supply floor.
  - :1020: no fee only when redeeming the whole supply.
- docs/SPECIFICATION.md:65-67, :408-410; KL-5 (:482-485).

**Description.**

KL-5 says that a fraction of GRET held elsewhere keeps the others from redeeming the last GRET normally
"until it is handed over". Anyone can make that fraction impossible to hand over:

1. Mint 1 wei of GRET. In the test basket this costs 7 base units of components; at the pilot's amounts,
   about one base unit per component.
2. Send it to an address that can never transfer it.

Nobody can then hold the whole supply, so the last holders can never redeem their last GRET normally. In
aggregate that is at most 1 GRET minus the dust.

- Only governance's irreversible liquidation releases it.
- With a hostile or lost governance, it cannot leave during a notice, or ever.

KL-5 presents the outside GRET as coming from a tiny mint or from fee GRET, and as something that can be
handed over. That a third party can make the hold-back permanent at will is more severe than described.

**Impact.** At most 1 GRET in aggregate, about USD 100 at the pilot's initial amounts, can leave only
through liquidation.

**Proof.** `test_C13_deadDustHoldsBackTheLastGretUntilLiquidation`:

- Carol mints 1 wei for 7 base units and sends it to `0x...dEaD`.
- After Alice leaves, Bob's `redeem` and `redeemSkipping` of 1 GRET revert with `SupplyBelowMinimum(1)`.
- He can redeem 1 wei, after which even 1 wei more reverts with `SupplyBelowMinimum(1e18 - 1)`.
- After `activateLiquidation`, he converts and claims about 2e18 H and 5e18 F.

Command: `npx hardhat test solidity test/audit/C13_UnrecoverableDust.t.sol -vv`

Result: 1 passing.

### GRET-11: Proposals pending at a governance handover or a key loss stay executable

**Severity:** Informational.

**Location.**

- contracts/GRETVault.sol:
  - :889-894: `acceptGovernance` clears only its own proposal.
  - :836-841: `removeEligibility` keeps a pending proposal.
  - :557-562, :589-595, :624, :727, :778, :827-832: actions that the proposed rebalancer or anyone can
    execute.
- docs/SPECIFICATION.md:209-213, :236-238; KL-1, KL-4.

**Description.**

A handover leaves the previous governance's proposals in place. Those that anyone can execute (guard,
eligibility, component addition, write-off, fee raise) or that the proposed rebalancer can execute stay
executable through their windows.

The key-loss case:

- If the key is lost while an eligibility proposal is pending, anyone can apply it and nobody can remove
  it. The holders it refuses can then never redeem, although KL-1 says that after a key loss "redemption
  keeps working".
- After a key loss, the rebalancer can also never be revoked nor the guard replaced. KL-1 does not list
  either.

Why this is only Informational:

- Every one of these actions keeps its full notice, so holders can leave first.
- The outcome is what KL-4 accepts for an appointed contract, and what :236-238 implies, since anyone
  applies a ready one.
- Only KL-1's summary and the silence of :209-213 are inaccurate.

**Verification.** A test written for this audit confirms the eligibility case:

- An eligibility contract proposed before a handover is applied by anyone after it.
- The holder is refused (`NotEligible`), and the former governance cannot remove it.
- Transfers still work.

**Recommended fix.**

- State that a handover keeps pending proposals, and that the new governance cancels what it does not
  want.
- Qualify KL-1: redemption keeps working after a key loss unless an eligibility contract was appointed or
  proposed before it. After a key loss, the rebalancer can never be revoked nor the guard replaced.

### GRET-12: A 1-wei redemption under a positive redemption fee burns nothing and pays nothing

**Severity:** Informational.

**Location.**

### GRET-15: The guard prices the requested sell amount, not what leaves the vault

**Severity:** Informational.

## 4. Specification and code disagreements not reported as findings

Every disagreement we found between the specification and the code is reported as a finding:

- In behavior: GRET-01, -02, -03, -05, -06, -07, -09 and -13.
- Known limitations that understate the consequences: GRET-04 and -11.
- Wording: GRET-08 and -10.
- NatSpec: GRET-14.

The points below were raised during the review and checked. They are not disagreements, and some come with
optional wording.

1. **Appointments during liquidation.** During liquidation, `acceptRebalancer`, `applyPriceGuard`,
   `applyEligibility`, `acceptGovernance` and `applyFees` still execute. docs/SPECIFICATION.md:281-283
   says appointments and fee settings remain callable and affect no claim.
2. **Small initial amounts.** :356-357 recommends initial amounts of at least about 10,000 base units, while
   the pilot configuration sets cbBTC to 3,081. That is a recommendation, the configuration is out of
   scope, and the constructor only requires positive amounts. One unit of rounding is 0.03% of cbBTC's
   amount per GRET.
3. **Missing events.** `addComponent` sets `excluded` without `ComponentActivationChanged`, and the
   constructor emits no `ComponentAdded`. The specification promises neither event.
4. **Activating a reverting component.** Governance can activate a component that reverts, at once, which
   makes `redeem` and `previewRedeem` revert. That does not contradict "Normal redemption is never paused"
   (:69-71):
   - That sentence is about the pause.
   - Activation is immediate by design (:91-92, KL-1).
   - A failing component is handled by skipping it (:191-192, :385-386, KL-10).

   Because activation does not change the version, a safe exit should skip every registered component the
   holder does not trust, excluded ones included (see GRET-01).
5. **The 128-component cap and gas.** contracts/GRETVault.sol:44-45 says the cap keeps mint and redemption
   within the gas limit. This holds for tokens of ordinary cost (section 5), and KL-10 says the cap cannot
   bound arbitrary issuer code.
6. **Long `balanceOf` answers in claims.** :327 says that a reverting or malformed `balanceOf` blocks that
   component's claim, while an answer longer than one word is accepted. The specification defines a
   failing read as one that reverts or answers with less than one word (:165-166, :231-232), and a longer
   answer decodes to its first word.
7. **Confiscated balances.** KL-10 speaks of claims that wait for recovery, while some issuers can destroy
   the vault's balance (PAXG's `wipeFrozenAddress`, exercised on a fork). The vault treats a destroyed
   balance as the specified loss: a smaller basis or a haircut (:300-306, :324-325). Naming confiscation in
   KL-10 would help.
8. **Leftovers after a full exit.** A normal full exit leaves excluded balances in the vault, and OA-6
   speaks of resuming minting. This matches :36-37, :96-97 and KL-3. Optionally, OA-6 could ask governance
   to pause minting before the supply reaches zero when leftovers must be decided first.
9. **"A small mint" in KL-8.** One unsolicited unit makes a sold-out component required again, and then
   any mint of up to the current supply asks it for one unit, not only a small one. The trigger, the
   consequence and the remedy are documented (KL-8, KL-11, `deactivateEmptyComponent`). Optional wording:
   "any mint of up to the current supply".
10. **Weekend staleness.** Feeds that update only on weekdays and OA-10's "normal operation" are
    compatible: :184-185 says feeds may go stale on weekends, and the guard refuses stale prices by design.
11. **Size of the feed lag.** KL-2 gives no size for the lag but says feeds lag "within their deviation
    thresholds", so a swap can lose the 2% limit plus that threshold at market prices. About 4% for
    cbBTC/USD, estimating thresholds from 45 consecutive rounds per feed. Optional: state the bound.
12. **Chainlink aggregator changes.** Chainlink can switch the aggregator behind a feed proxy without the
    vault's notice. The guard reads feed decimals on every valuation. Optional: mention this in KL-2, as

### Additional properties

Share accounting:

- Round trips never profit.
- No unbacked GRET can be minted.
- Every vault-side division rounds against the caller: inputs up, issuance down, outputs down, fees up and
  claims down.
- Share-converting tokens never debit or credit more than the amount (fuzz).
- `_update` is the only ERC-20 override.

Rebalancing:

- Mints and redemptions around swaps do not stretch the weekly limit: the recorded share equals what each
  GRET loses (test).
- Components without a feed are refused on both sides and count as zero.
- The real feeds have 8 decimals, `minAnswer` 1 and `maxAnswer` about 9.58e52, so `answer * 1e18` cannot
  overflow.
- There is no pool to sandwich.
- Feeds, maximum ages and limits change only through a new guard, after notice.

Reentrancy, roles and OpenZeppelin:

- The only transient storage is OpenZeppelin's reentrancy lock.
  - A reverted frame undoes it, and the vault has no inline assembly that could skip the modifier.
  - TLOAD works under STATICCALL.
  - Tests catch failed guarded calls and continue in the same transaction.
- Static reads compile to STATICCALL. A token whose `balanceOf` tries to apply a ready eligibility
  contract changes nothing (test).
- Roles:
  - Governance and the rebalancer accept their own appointment.
  - Zero addresses are refused, and there is no renounce.
  - Without a rebalancer or a guard nobody can swap.
- Permit: signatures are used once, nonces advance, and expired deadlines revert.
- OpenZeppelin 5.6.1: SafeERC20 semantics and `Math.mulDiv` rounding are used as documented, and every
  denominator is nonzero at its call site.

### GRET-01: fixed

**Change.**

- `redeem` and `redeemSkipping` call `_requireBasketForLimits`, which checks the version and the length
  only when some minimum is positive. Minima that are all zero, or an empty array, limit nothing, so they
  are not tied to a version.
- The minima loop reads `amounts[i]` only for a positive minimum, so zero minima of any length are safe.
- `_skipMask` ignores listed addresses that are not components, instead of reverting with
  `NotAComponent`.

**Why the first change is not enough on its own.** The fix work turned up a second path with the same
effect:

- A token announced for the basket can be added by anyone and activated at once by governance.
- Once it is active, every exit that does not skip it calls it, so a token whose calls revert refuses
  those exits.
- Each refusal costs one announcement made a week earlier. The churn in GRET-01 gets two refusals from
  each announcement.

At `fabc144` this path added nothing to GRET-01:

- Every change of version already refused prepared redemptions.
- `redeemSkipping` could not list a token before it joined.

The second change lets an exit prepared in advance list every announced token, so activating one later
cannot refuse it.

**Result.** At any time, a holder can prepare an exit that no basket change refuses during the following
notice. The exit is a `redeemSkipping` call with zero minima. Its list names every token announced for
the basket and every component other than the active ones the holder wants, excluded components
included.

- Every addition needs an announcement made at least seven days earlier (`ComponentAnnounced`), so that
  list is complete for a transaction sent within the week.
- At most 128 tokens can be announced and waiting at once (`6356b01`, under "Second review"), so the list
  always fits in one transaction. Without that cap, a governance could announce more tokens than a
  transaction can list.
- The holder accepts what swaps the guard allows until the exit executes.
- Redemptions with a positive minimum stay tied to the version, as the specification requires.

**Documentation.** docs/SPECIFICATION.md (skipping, the component lifecycle and KL-1) and the README
describe the new rule. KL-1 now also says two things:

- A positive minimum can still be refused throughout a notice.
- An exit prepared in advance must list the announced tokens.

**Verification.**

- `test/GRETVault.protections.t.sol::test_redemptionsWithoutMinimaIgnoreBasketChanges`:
  - Three changes of version happen during a hostile notice.
  - A prepared redemption with a positive minimum reverts with `BasketChanged`.
  - Four redemptions prepared with zero minima or none, through both functions, pay Bob in full.
- `test/GRETVault.protections.t.sol::test_preparedExitSkipsAnnouncedTokenBeforeItJoins`:
  - Bob lists an announced token and an address outside the basket.
  - The token joins, is activated and reverts on every call.
  - Bob's prepared exit pays him in full.
- Both tests fail against the vault at `fabc144` (2 failing) and pass from `c107549` on.
- `test/GRETVault.limitations.t.sol::test_activatedNewcomerRefusesExitsThatDoNotSkipIt` reproduces the
  limitation that remains.
- The audit's tests at `8ed0664`, and again at `a462ed9`: `C01_VersionChurn.t.sol` (2 tests) and
  `N02_ChurnWithEligibility.t.sol` (1 test) now fail. Each expects a prepared redemption with zero minima to revert with `BasketChanged`,
  and the redemption goes through instead:
  - The churn test stops at "a prepared redemption went through".
  - The other two report "next call did not revert as expected".
  - In N02, Bob's own prepared exit no longer needs a router, so the eligibility contract's check of the
    caller no longer matters.

**Side effect.** A `redeemSkipping` call whose list names only addresses outside the basket used to
revert with `NotAComponent`. It now pays like `redeem`, and if it empties the supply it pauses minting,
like any skipping redemption.

**Not changed.** The pilot redemption flow (`scripts/pilot/plan.ts`, out of scope) still sends the minima
from `previewRedeem`. They are positive, so the flow stays tied to the version. In a hostile notice a
holder would send zero minima instead.

### GRET-03: fixed

**Change.**

  32-byte output area, so only the first word of the answer is copied.
  - The answer's size is still checked: at least one word for balances, exactly one word for the
    predecessor's count.
  - A read that fails, answers less than one word or needs more gas counts as zero, as the specification
    already said.

  `decimals()` read that the GRET-05 fix added to every valuation, which an issuer could otherwise make
  burn the swap's gas.

  was estimated with `eth_estimateGas` on mainnet, transaction overhead subtracted.

**Verification.**

- `test/GRETVault.protections.t.sol`:
  - `test_oversizedBalanceReadDoesNotBlockRescue` and `test_balanceReadsThatBurnTheirGasDoNotBlockRescue`:

**What remains.**

- A component whose read needs more than 200,000 gas counts as zero:
  - In `rescue`, its balance is then not compared after the transfer.
  - In the guard, it adds nothing to the vault's value, which makes the weekly fraction more
    conservative.
- Mint, redemption and swaps still read the components involved without a cap, as KL-10 describes, so an
  issuer can still block them until holders skip the component or governance writes it off.

## 3. Verified findings

### GRET-001 — Receipt tolerance overflows for valid near-maximum inputs

**Severity: Low. Status: verified, unfixed.** Location: `contracts/GRETVault.sol:1004`, reached by mint at `:328`. Relevant specification: `docs/SPECIFICATION.md:31–33,46–49`.

The shared `_pull` helper measures receipt and rejects zero, excess or excessive shortfall:

```solidity
if (received == 0 || received > amount || received + MAX_RECEIPT_SHORTFALL < amount) {
    revert UnexpectedBalance(index, amount, received);
}
```

With `MAX_RECEIPT_SHORTFALL = 10`, the addition overflows for the top ten `uint256` values, even when receipt equals the request. The specification permits positive exact receipts and does not exclude these configured initial amounts. A standard mock with maximum supply produces a valid bootstrap preview but the actual mint reverts with `Panic(0x11)`.

**Impact and likelihood.** The extreme configuration cannot bootstrap until governance lowers the initial amount. Funds and GRET supply roll back completely. This requires economically unrealistic supply/configuration; no impact on the eleven pilot assets, loss, notice bypass or privileged callback is demonstrated. The same helper is called by swaps at `GRETVault.sol:563`; that is source-supported exposure, not a separately executed maximum-input swap finding.

**Executed proof.** The following is the exact test function from `test/GRETVault.audit-stage2.t.sol`, in `GRETVaultAuditStage2Test is GRETVaultCase`. The file imports the frozen `MockERC20`, `GRETVault`, `IERC20` and `test/helpers/GRETVaultCase.sol`; the harness supplies `SHARE`, actors and `_one`. It first proves the panic/rollback, then changes only the configured amount to `uint256.max - 10` and proves success.

```solidity
function test_receiptToleranceOverflowsForAnOtherwiseValidMaximumReceipt() public {
    MockERC20 huge = new MockERC20("Maximum supply", "MAX", 18);
    IERC20[] memory basket = new IERC20[](1);
    basket[0] = huge;
    GRETVault target = new GRETVault(basket, _one(type(uint256).max), GOVERNANCE);
    huge.mint(ALICE, type(uint256).max);
    vm.prank(ALICE);
    huge.approve(address(target), type(uint256).max);
    assertEq(target.previewMint(SHARE)[0], type(uint256).max);

    vm.expectRevert(abi.encodeWithSignature("Panic(uint256)", 0x11));
    vm.prank(ALICE);
    target.mint(SHARE, ALICE, _one(type(uint256).max), SHARE, 0);
    assertEq(target.totalSupply(), 0);
    assertEq(huge.balanceOf(address(target)), 0);
    assertEq(huge.balanceOf(ALICE), type(uint256).max);

    vm.prank(GOVERNANCE);
    target.setInitialAmounts(_one(type(uint256).max - 10), 0);
    vm.prank(ALICE);
    (uint256 minted,) = target.mint(SHARE, ALICE, _one(type(uint256).max), SHARE, 0);
    assertEq(minted, SHARE);
    assertEq(huge.balanceOf(address(target)), type(uint256).max - 10);
}
```

Historical targeted command:

```sh
npx hardhat test solidity test/GRETVault.audit-stage2.t.sol
```

The retained conversation records exit 0 and four passing cases for that command; its original raw log was lost. The exact recovered test subsequently ran successfully in the fresh recovery `npm run check` (299 passing), the latest complete default check (314 passing) and the deep execution (176 Solidity passing). Thus the present finding is supported by fresh retained execution, not only a reconstructed historical summary. See complete test (`test/GRETVault.audit-stage2.t.sol`), fresh recovery log (`audit-work/logs/recovery-npm-run-check.log`) and latest default log (`audit-work/logs/stage5b2-npm-run-check.log`).

**Recommended fix.** After rejecting zero/excess receipt, compare the shortfall by subtraction:

```solidity
if (received == 0 || received > amount || amount - received > MAX_RECEIPT_SHORTFALL) {
    revert UnexpectedBalance(index, amount, received);
}
```

Short-circuit ordering makes the subtraction safe. Retain a boundary regression and verify mint and swap paths after any change. This recommendation has not been applied or validated as a patch in the frozen source.

### GRET-002 — Aggregate bounded reads block unrelated rescues at maximum basket size

**Severity: Low. Status: verified, unfixed.** Locations: `contracts/GRETVault.sol:893` (all-component pre-read), `:898` (positive-balance post-read), `:1172` (200,000-gas staticcall). Relevant specification: `docs/SPECIFICATION.md:247–259`; broader issuer-cost limitation: `:574–577`.

Rescue snapshots every registered component, transfers the selected token and rereads every other component with a positive pre-balance to protect against alias-ledger depletion. The individual reads are bounded, but the total work is not budgeted against the 16,777,216 transaction limit. With 128 components, one healthy plus 127 adverse readers can exhaust the transaction budget even when the rescued token is ordinary and unrelated. Both truthful reads costing at least 180,000 gas and reads exhausting their stipend reproduce the failure.

**Impact and prerequisites.** The test starts with conforming readers, a valid basket and a successful foreign rescue. Readers are made adverse only afterwards, modeling later issuer deviation rather than an admission/notice bypass. Of 100 donated foreign units, 99 remain unavailable through rescue while the adverse behavior persists. No foreign balance moves in a failed transaction. The proof successfully activates liquidation, converts shares and claims the healthy registered asset; foreign rescue still fails afterwards. Issuer read restoration restores rescue. In liquidation the component list cannot be shortened; write-off/exclusion alone does not remove slots from the rescue scan. No healthy-holder exit blockage, transfer theft or holder-accounting loss was demonstrated. Recovery of a removed former component through external distribution could encounter this limitation, but that separate path was not reproduced.

**Likelihood and classification.** This requires a synthetic maximum-size configuration with many adverse readers. The corresponding eleven-component controls pass, so no actual pilot failure is established. The specification explicitly accepts issuer-cost limitations and says the 128-component cap does not bound arbitrary issuer code. That is material counterevidence. The narrower rescue promise nevertheless says failed/over-budget component reads do not block other-token rescues, despite enumerating all slots with per-read limits. The reproduced violation of that specific promise supports **Low** severity. It is not a Medium/High claim about ordinary redemption or liquidation claims.

**Proof and results.** The complete executed Node proof and adversarial reader code are embedded in Appendix A. The fixture deploys one healthy asset and 127 readers, sets a healthy-only bootstrap through authorized governance, donates positive reader backing, mints one GRET and donates the foreign asset. It asserts statuses, declared gas, empty access lists, unchanged balances/supply and healthy claim delivery. Commands:

```sh
npx hardhat test nodejs test/GRETVault.audit-stage4b.ts
npx hardhat test solidity test/GRETVault.audit-stage4b.t.sol
```

Both exited 0: two Node cases and three Solidity cases. The Node cases supply the aggregate-gas proof/control; the Solidity cases additionally test alias and malformed-return protections. Node log (`audit-work/logs/stage4b-targeted-node.log`), Solidity log (`audit-work/logs/stage4b-targeted-solidity.log`). Every measured transaction below declares exactly **16,777,216 gas**, with no access list, under a separately enforced transaction cap.

**Recommended fix.** Derive supported cardinality/read allowances from a complete two-pass transaction budget, including overhead and transfer margin, while retaining alias protection. Revalidate real issuer read costs before lowering per-read allowances. Skipping positive post-checks when gas is low would weaken backing protection and is not a safe mechanical fix. If this aggregate limitation is intentionally accepted, narrow the rescue guarantee explicitly and document the recovery consequences. No fix was applied.

## 4. Specification comparison and related observations

No additional verified code/specification disagreement was identified beyond GRET-001 and GRET-002. This is a bounded review conclusion, not an exhaustive equivalence proof. The frozen specification's statement that no independent audit had yet occurred describes its publication date; it is not a contract behavior finding or a reason to edit the frozen target.

**H-003 — reproduced aggregate guard-gas limitation, not another finding.** `ChainlinkPriceGuard.sol:218–230` separately bounds balance/valuation calls but does not bound their aggregate. In `test/GRETVault.audit-stage5b2.ts`, a supported 128-component basket contains two healthy traded assets and 126 unrelated adverse readers. A 100-for-99 exchange loses 1% of sell value, below the 2% trade cap; even three losses are less than 0.16% of the healthy priced denominator, below the weekly cap. Under declared gas 16,777,216, expensive/exhausted-reader losing swaps nevertheless revert using 16,516,323 gas. Finite allowance, balances, supply and guard state roll back. Same-state fair swaps succeed at 119,013 gas; restored-read losses succeed at 3,269,113; a healthy skipping exit succeeds at 596,246 while **forfeiting all 126 skipped balances**. Eleven-component controls succeed. Targeted `npx hardhat test nodejs test/GRETVault.audit-stage5b2.ts` and full `npm run check` exited 0. Proof (`test/GRETVault.audit-stage5b2.ts`), log (`audit-work/logs/stage5b2-targeted.log`), economic controls (`audit-work/STAGE-05B2.md`).

The guard specification at lines 177–181 promises conservative per-read omission, without an unconditional aggregate losing-swap availability promise; lines 574–577 accept broad issuer-cost limitations. Warranted delayed write-off/exclusion can omit guard reads at line 223, a governance-dependent recovery mechanism supported by source but not executed as a recovery sequence here. Rescue has a stronger explicit promise and retains excluded slots. Accordingly H-003 is neither refuted nor counted again as a finding. No actual pilot failure, healthy-exit blockage or accounting loss was demonstrated.

**Notices and accepted trust limits.** No notice bypass or healthy-asset exit failure was reproduced in the examined sequences. This does not establish unconditional exit availability: positive-minimum exits can be invalidated by basket-version churn; prepared zero-minimum exits accept economic changes and must pre-skip announced or unwanted components, including ones governance may reactivate. Skipping abandons those assets. Unskipped issuer failures can block normal exits, and the normal supply floor can require governance-triggered liquidation. Once liquidation is active, the tested healthy claims remain independent of broken unrelated tokens and later eligibility/guard/fee appointments. Issuer failure can still block that issuer's own claim. These distinctions follow the specification rather than turning its disclosed limitations into new findings.

Other retained assumptions include careful admission without transfer fees/callbacks/alias ledgers; issuer and corporate-action monitoring; justified write-offs and recovery handling; fixed-base-unit tolerances; loss of outgoing delivery/debit guarantees under adverse issuers; malicious governance replacing the guard after notice; address notices that do not freeze upgradeable behavior; fixed-week boundary exposure of approximately 4% within some seven-day intervals; offchain price accuracy/depeg/split risk; and pro-rata late recovery rather than targeted compensation. The specification's operating assumptions are not all enforced by code. Tests that reproduce their accepted consequences are evidence of limits, not fixes.

```solidity
contract Stage4BReadToken is CaseToken {
    // 0: normal; 1: short; 2: oversized; 3: revert;
    // 4: spend at least 180,000 gas and return the truthful balance;
    // 5: exceptional halt consuming all forwarded gas.
    uint8 public readMode;
    address public aliasAddress;

    constructor() CaseToken("Stage 4B reader") {}

    function configure(uint8 mode) external { readMode = mode; }
    function setAliasAddress(address next) external { aliasAddress = next; }

    function moveFrom(address from, address to, uint256 amount) external {
        require(msg.sender == aliasAddress, "only alias");
        _transfer(from, to, amount);
    }

    function rawBalanceOf(address account) external view returns (uint256) {
        return super.balanceOf(account);
    }

    function balanceOf(address account) public view override returns (uint256 amount) {
        amount = super.balanceOf(account);
        uint8 mode = readMode;
        if (mode == 1) {
            assembly ("memory-safe") {
                mstore(0, amount)
                return(0, 31)
            }
        }
        if (mode == 2) {
            assembly ("memory-safe") {
                mstore(0, amount)
                return(0, 65536)
            }
        }
        if (mode == 3) revert("unreadable");
        if (mode == 4) {
            uint256 start = gasleft();
            while (start - gasleft() < 180_000) {}
        }
        if (mode == 5) {
            assembly ("memory-safe") { invalid() }
        }
    }
}
```

The complete Node proof below is `test/GRETVault.audit-stage4b.ts`, executed with the command in GRET-002. Deployments resolve the reader above and frozen vault/mock artifacts through Hardhat. Its baseline, eleven-component control, failed rescue/rollback, independent healthy claim and issuer-restoration sequence are part of the executed evidence.

```typescript
import assert from "node:assert/strict";
import { after, describe, it } from "node:test";
import { network } from "hardhat";
import { type Hash } from "viem";

const SHARE = 10n ** 18n;
const GAS_CAP = 16_777_216n;

describe("GRET audit stage 4B: cold aggregate rescue gas", async () => {
  // Runtime test settings only. Reverted transactions produce receipts.
  // The transaction cap is enforced independently of the block limit.
  const connection = await network.create({
    network: "hardhat",
    override: {
      blockGasLimit: 30_000_000n,
      transactionGasCap: GAS_CAP,
      throwOnTransactionFailures: false,
    },
  });
  const { viem } = connection;
  const publicClient = await viem.getPublicClient();
  after(() => connection.close());

  async function ok(pending: Promise<Hash>) {
    const receipt = await publicClient.waitForTransactionReceipt({ hash: await pending });
    assert.equal(receipt.status, "success", "setup/control transaction failed");
    return receipt;
  }

  async function measured(pending: Promise<Hash>, expectedStatus: "success" | "reverted") {
    const hash = await pending;
    const receipt = await publicClient.waitForTransactionReceipt({ hash });
    const transaction = await publicClient.getTransaction({ hash });
    assert.equal(receipt.status, expectedStatus);
    assert.equal(transaction.gas, GAS_CAP);
    assert.ok(receipt.gasUsed <= GAS_CAP);
    assert.ok(!transaction.accessList || transaction.accessList.length === 0);
    return {
      status: receipt.status,
      declaredGas: transaction.gas.toString(),
      gasUsed: receipt.gasUsed.toString(),
    };
  }

  async function fixture(count: number) {
    const [, governance, alice, receiver] = await viem.getWalletClients();
    const healthy = await viem.deployContract("MockERC20", ["Healthy", "H", 18]);
    const foreign = await viem.deployContract("MockERC20", ["Foreign", "F", 18]);
    const deployReader = () => viem.deployContract("Stage4BReadToken");
    const readers: Awaited<ReturnType<typeof deployReader>>[] = [];
    for (let i = 1; i < count; ++i) {
      readers.push(await deployReader());
    }
    const initial = [100n, ...readers.map(() => 1n)];
    const vault = await viem.deployContract("GRETVault", [
      [healthy.address, ...readers.map((token) => token.address)],
      initial, governance.account.address,
    ]);
    // Constructor amounts must be positive. Then governance sets a healthy-only
    // bootstrap. Positive donations belong to its first holder; each is above dust.
    const bootstrap = [100n, ...readers.map(() => 0n)];
    await ok(vault.write.setInitialAmounts([bootstrap, 0n], { account: governance.account }));
    for (const token of readers) await ok(token.write.mint([vault.address, 100n]));
    await ok(healthy.write.mint([alice.account.address, 100n]));
    await ok(healthy.write.approve([vault.address, 100n], { account: alice.account }));
    await ok(vault.write.mint(
      [SHARE, alice.account.address, bootstrap, SHARE, 0n],
      { account: alice.account, gas: GAS_CAP },
    ));
    await ok(foreign.write.mint([vault.address, 100n]));

    async function setMode(mode: number) {
      for (const token of readers) await ok(token.write.configure([mode]));
    }
    function rescue() {
      return vault.write.rescue(
        [foreign.address, receiver.account.address, 1n],
        { account: governance.account, gas: GAS_CAP },
      );
    }
    async function assertReaderBacking() {
      for (const token of readers) {
        assert.equal(await token.read.rawBalanceOf([vault.address]), 100n);
        assert.equal(await token.read.rawBalanceOf([receiver.account.address]), 0n);
      }
    }
    assert.equal(await vault.read.componentCount(), BigInt(count));
    assert.equal(await vault.read.totalSupply(), SHARE);
    return { vault, healthy, foreign, readers, governance, alice, receiver,
      setMode, rescue, assertReaderBacking };
  }

  it("eleven components tolerate expensive and exhausted bounded reads", async (t) => {
    const f = await fixture(11);
    t.diagnostic(JSON.stringify({ scenario: "11-cheap-baseline",
      ...await measured(f.rescue(), "success") }));
    await f.setMode(4);
    t.diagnostic(JSON.stringify({ scenario: "11-ten-expensive-positive-readers-two-passes",
      ...await measured(f.rescue(), "success") }));
    await f.setMode(5);
    t.diagnostic(JSON.stringify({ scenario: "11-ten-exhausted-pre-readers",
      ...await measured(f.rescue(), "success") }));
    assert.equal(await f.foreign.read.balanceOf([f.vault.address]), 97n);
    assert.equal(await f.foreign.read.balanceOf([f.receiver.account.address]), 3n);
    assert.equal(await f.healthy.read.balanceOf([f.vault.address]), 100n);
    assert.equal(await f.vault.read.totalSupply(), SHARE);
    await f.assertReaderBacking();
  });

  it("128-component rescue failure remains separate from healthy claim exits", async (t) => {
    const f = await fixture(128);
    t.diagnostic(JSON.stringify({ scenario: "128-cheap-baseline",
      ...await measured(f.rescue(), "success") }));
    await f.setMode(4);
    t.diagnostic(JSON.stringify({ scenario: "128-127-expensive-positive-readers",
      ...await measured(f.rescue(), "reverted") }));
    assert.equal(await f.foreign.read.balanceOf([f.vault.address]), 99n);
    assert.equal(await f.foreign.read.balanceOf([f.receiver.account.address]), 1n);
    assert.equal(await f.healthy.read.balanceOf([f.vault.address]), 100n);
    assert.equal(await f.vault.read.totalSupply(), SHARE);
    assert.equal(await f.vault.read.liquidationActive(), false);
    await f.assertReaderBacking();

    await f.setMode(5);
    t.diagnostic(JSON.stringify({ scenario: "128-127-exhausted-pre-readers",
      ...await measured(f.rescue(), "reverted") }));
    assert.equal(await f.foreign.read.balanceOf([f.vault.address]), 99n);
    assert.equal(await f.foreign.read.balanceOf([f.receiver.account.address]), 1n);
    t.diagnostic(JSON.stringify({ scenario: "128-liquidation-activation-with-broken-readers",
      ...await measured(f.vault.write.activateLiquidation({
        account: f.governance.account, gas: GAS_CAP,
      }), "success") }));
    t.diagnostic(JSON.stringify({ scenario: "128-conversion-with-broken-readers",
      ...await measured(f.vault.write.convertToClaims([SHARE], {
        account: f.alice.account, gas: GAS_CAP,
      }), "success") }));
    t.diagnostic(JSON.stringify({ scenario: "128-independent-healthy-claim",
      ...await measured(f.vault.write.claim(
        [0n, f.receiver.account.address, 100n],
        { account: f.alice.account, gas: GAS_CAP },
      ), "success") }));
    assert.equal(await f.healthy.read.balanceOf([f.receiver.account.address]), 100n);
    assert.equal(await f.healthy.read.balanceOf([f.vault.address]), 0n);
    assert.equal(await f.vault.read.totalSupply(), 0n);
    assert.equal(await f.vault.read.liquidationSupply(), SHARE);
    assert.equal(await f.vault.read.convertedShares([f.alice.account.address]), SHARE);
    assert.equal((await f.vault.read.totalPaid())[0], 100n);
    t.diagnostic(JSON.stringify({ scenario: "128-foreign-rescue-still-blocked-after-healthy-exit",
      ...await measured(f.rescue(), "reverted") }));
    assert.equal(await f.foreign.read.balanceOf([f.vault.address]), 99n);
    assert.equal(await f.foreign.read.balanceOf([f.receiver.account.address]), 1n);

    // Issuer cooperation is a recovery control, not a vault governance power
    // or evidence that actual issuers will cooperate.
    await f.setMode(0);
    t.diagnostic(JSON.stringify({ scenario: "128-foreign-rescue-after-issuer-read-recovery",
      ...await measured(f.rescue(), "success") }));
    assert.equal(await f.foreign.read.balanceOf([f.vault.address]), 98n);
    assert.equal(await f.foreign.read.balanceOf([f.receiver.account.address]), 2n);
    await f.assertReaderBacking();
  });
});
```
